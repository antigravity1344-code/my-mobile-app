# مرز امنیتی آفلاین — مرحلهٔ چهارم

مأموریت `PAKSHO-AGENT-MANAGER-SECURITY-004`، دستور PR #9 نظر 6128564865، مبنا `e2365404bba64f72d0a5d5aef6c786873fbd9c23`.

## ساخته‌شده: مهار ورودی

| کنترل | حد و محل اجرا |
| --- | --- |
| بایت خام | هر فرمان stdin و هر فایل تنظیمات حداکثر 262144 بایت؛ خواندن جریان‌دار، رد پیش از نگهداری قطعهٔ عبورکننده از حد و پیش از JSON.parse |
| زمان خواندن | مهلت مطلق 5000ms برای هر جریان از شروع خواندن؛ ورود تدریجی داده آن را تمدید نمی‌کند |
| رمزگذاری | TextDecoder با fatal؛ UTF-8 نامعتبر رد می‌شود. BOM جزو JSON معتبر پذیرفته نمی‌شود |
| عمق | حداکثر 32 ظرف object/array، ریشهٔ ظرف عمق 1؛ اسکن پیش از parse با تشخیص رشته و escape |
| اعضا | حداکثر 10000 کلید شیء/عنصر آرایه در کل داده؛ پس از parse و پیش از hash |
| canonical | حداکثر 262144 بایت، مستقل از سقف ورودی خام؛ سقف گزارش 32768 بایت قبلی محفوظ |
| شکل فرمان | شیء غیرآرایه، نوع شناخته‌شده، allowlist فیلدها و انواع مقدماتی؛ اعتبارسنجی معنایی/فیلدهای لازم همچنان در هسته |

`parseBounded` فقط Buffer می‌پذیرد. JSON.parse بعد از کنترل بایت، UTF-8 و عمق اجرا می‌شود؛ کنترل اعضا پس از parse است. بنابراین ادعای شمارش اعضا پیش از parse نداریم. escapeها ممکن است اندازهٔ canonical را با ورودی خام متفاوت کنند و هر دو حد جداگانه اعمال می‌شوند. JSON grammar با JSON.parse کنترل می‌شود، شامل رفتار استاندارد آن برای کلیدهای تکراری؛ این نسخه تشخیص اختصاصی duplicate key ندارد.

`Manager.execute` نیز پیش از hash، canonical محدود و شکل فرمان را بررسی می‌کند. دادهٔ درون‌فرایندی باید JSON ساده باشد؛ چرخه، getter، prototype سفارشی و مقدار غیر JSON رد می‌شود. Proxy مخربِ جاوااسکریپت و کد دلخواه داخل همان فرایند بیرون مرز اعتماد است. منابع سیستم‌عامل و تعداد فرایندهای هم‌زمان با این ابزار محدود نمی‌شوند؛ این مهلت، سقف کل اجرای DB یا CPU نیست. ورودی فشرده پشتیبانی نمی‌شود.

در CLI ورودی/تنظیمات نامعتبر پیش از بازکردن DB رد می‌شود. در Manager رد بودجه/شکل پیش از تراکنش است؛ خطای معنایی داخل تراکنش همچنان فقط ساعت monotonic را می‌تواند جلو ببرد. task، resource، event، outbox و command receipt تغییر ناقص نمی‌کنند. هیچ migration یا حذف داده انجام نشده است.

## ساخته‌شده: صفحه‌بندی

CLI برای `events` و `pending-reports` پاسخ `{items, snapshot, nextCursor}` می‌دهد. `limit` پیش‌فرض 100 و بازهٔ مجاز 1 تا 500 است. سقف پاسخ 1048576 بایت UTF-8 **با newline** است؛ ممکن است پیش از limit صفحه پر شود. گزارش‌ها در میانه قطع نمی‌شوند.

```json
{"type":"events","taskId":"DEMO-CLI-001","limit":100}
```

در درخواست بعد، همان `nextCursor` را در `cursor` بگذارید. cursor شامل نوع مجموعه، taskId (برای outbox برابر null)، آخرین seq/id و snapshot سقف توالی است. مرتب‌سازی صعودی و keyset است؛ append بعدی وارد همان پیمایش نمی‌شود. cursor رمزنگاری/امضا نشده و مجوز دسترسی نیست؛ تغییر آن به معنی انتخاب محدودهٔ دیگر است. تطابق نوع/مأموریت و حدود عددی بررسی می‌شود. از cursor جعلی برای snapshot معتبر یا اثبات تمامیت استفاده نکنید.

outbox در هر صفحه فقط رکوردهای هنوز تحویل‌نشده را نشان می‌دهد؛ ثبت receipt میان صفحات می‌تواند رکورد را از ادامه خارج کند. این snapshot ثابتِ عضویت pending نیست، بلکه سقف ثابت توالی است. رکورد دریافت‌شده ولی بی‌رسید در polling تازه بازمی‌گردد؛ پس بعد از پایان پیمایش، برای retry و داده‌های تازه بدون cursor شروع کنید. هیچ outbox یا تاریخچه حذف نمی‌شود.

رکورد تاریخی منفرد بزرگ‌تر از صفحه با `PAGE_ITEM_TOO_LARGE:<id>` مشخص می‌شود؛ پیمایش از آن نمی‌پرد و رکورد باقی می‌ماند. اندازهٔ payload تاریخی در SQLite پیش از انتقال/parse به JS بررسی می‌شود. مسیر export یا تقسیم رکورد بزرگ هنوز ساخته نشده و نیازمند بررسی جداگانه است. سقف همهٔ پاسخ‌های CLI نیز با `boundedResponse` کنترل می‌شود.

متدهای قدیمی `events(taskId)` و `pendingReports()` برای مجموعهٔ قابل‌جاگیری در یک صفحه همچنان آرایه می‌دهند؛ برای بیش از یک صفحه `PAGINATION_REQUIRED` می‌دهند تا داده بی‌صدا گم نشود. API جدید: `eventsPage(taskId, {limit,cursor})` و `pendingReportsPage({limit,cursor})`. تنها تغییر آزمون‌های قبلی، بررسی envelope به‌جای آرایه در آزمون CLI است؛ همان تعداد رکورد و نبود ادامه همچنان بررسی می‌شود. برنامهٔ نمایشی کوچک بدون تغییر کار می‌کند.

## ساخته‌شده: قرارداد اعتماد آفلاین

`TrustedIngress` یک کنترل مجوز آفلاین است، **نه احراز هویت عملیاتی**. ورودی آن Buffer فرمان و یک handle خارج از payload است. سازنده یک تابع میزبان `resolveContext(handle)` دریافت می‌کند. میزبان باید handle را به هویت ازقبلتأییدشده، اثرانگشت دستور فعلی و تأیید مستقل مالک نگاشت کند. نمونهٔ امن برای آزمون، WeakMap از handleهای خصوصی به context است؛ کپی context از JSON ارسالی ممنوع است.

بدون resolver یا با handle ناشناس، `BLOCKED_FOR_REAL_AUTH` رخ می‌دهد و DB تغییر نمی‌کند. این آداپتور در CLI قدیمی نصب نشده است. CLI و Manager سطح پایین همچنان ابزارهای **محلیِ مورد اعتماد** هستند و دسترسی به فایل DB/تنظیمات و اجرای کد اختیار کامل می‌دهد. برای منبع غیرمطمئن، میزبان آینده باید فقط آداپتور را در دسترس بگذارد، نه CLI/Manager/DB را. اضافه‌کردن آداپتور، دورزدن آن از همان فرایند را غیرممکن نمی‌کند.

قرارداد context میزبان:

```js
{
  principalId: 'SUPERVISOR',
  kind: 'supervisor', // supervisor | worker | reporter | reader
  allowedCommands: ['register', 'get', 'events'],
  // worker additionally: role, agentId, runId (all host-derived)
  grant: {
    spec, // complete task definition including dependencies/resources/actions
    instructionFingerprint, // SHA-256 of current instruction, supplied by host
    approval: {
      ownerId, taskId, repository, sourceCommentId, baseSha,
      specFingerprint: scopeFingerprint(spec),
      instructionFingerprint,
      expiresAt // integer epoch milliseconds, must be greater than host clock
    }
  }
}
```

spec با همان اعتبارسنجی و نرمال‌سازی هسته (مرتب‌سازی فهرست‌ها و مقدار پیش‌فرض فهرست خالی) و سپس canonical با کلیدهای مرتب hash می‌شود؛ taskId، مخزن، comment ID، SHA مبنا و hash کل دامنه باید با تأیید مالک یکسان باشند. تغییر متن دستور با اثرانگشت قبلی رد می‌شود. صحت هویت مالک، اصل متن دستور و اصالت این context را **میزبان** باید تضمین کند؛ اثرانگشت به‌تنهایی تأیید GitHub یا مالک نیست. میزبان باید ساعت معتبر و سیاست لغو داشته باشد؛ عقب‌رفتن ساعت میزبان این آداپتور مهار نشده است.

در payload، actor/ownerApproved/agentId/runId/role/context/principalId/approval/grant رد می‌شوند. actor و مالک اجرا فقط از context می‌آیند؛ `ownerApproved:true` داخل فرمان هسته صرفاً پس از تطبیق تأیید مستقل میزبان تولید می‌شود و از JSON کاربر پذیرفته نمی‌شود. supervisor/reporter باید برای عملیات مربوط در allowlist محلی Manager نیز باشند.

| نقش | فرمان‌های ممکن، مشروط به allowedCommands و grant |
| --- | --- |
| supervisor | register، decide، retry، get، events |
| worker | claim، start، heartbeat، finish، get، events؛ نقش و run از میزبان |
| reporter | report-receipt، get، events؛ رسید فقط برای task همان grant و همچنان simulated |
| reader | get، events در task همان grant |

pending-reports سراسری در آداپتور رد می‌شود تا دادهٔ مأموریت دیگر افشا نشود؛ خواندن outbox از API پایین‌تر فقط برای میزبان محلی مجاز است. رخدادهای همان task مسیر خواندن محدودِ عامل هستند. تخصیص هویت و namespace عامل/اجرای یکتا و جداسازی مالک/تصویب‌کننده مسئولیت میزبان است.

شناسهٔ فرمان در آداپتور با hash از principalId، مخزن، taskId و شناسهٔ درخواستی جدا می‌شود. اثرانگشت رسید علاوه بر فرمان، kind، principalId، اثرانگشت scope/دستور و ownerId را در بر می‌گیرد. همان فرمان پس از بازگشایی DB پاسخ تاریخی می‌گیرد؛ payload یا binding متفاوت برای همان شناسه conflict می‌دهد. مجوز و انقضا پیش از replay دوباره بررسی می‌شوند. رسید تازه‌ای خارج تراکنش core اضافه نمی‌شود. این سازوکار جای dedup تحویل webhook آینده نیست.

## ساخته‌نشده و محدودیت اثر خارجی

هیچ ارائه‌دهندهٔ هویت، webhook، اعتبارنامه، تماس شبکه‌ای برنامه، GitHub Actions runner، اتصال گزارشگر زنده یا اجرای Codex/UX-UI ساخته نشده است. تست‌ها context ساختگی میزبان دارند و صرفاً قرارداد آفلاین را می‌سنجند. احراز هویت واقعی تا انتخاب میزبان/ارائه‌دهنده و اثبات اتصال هویت به مجوز **BLOCKED_FOR_REAL_AUTH** است.

fencing موجود فقط نوشتن در DB را کنترل می‌کند؛ عامل منقضی ممکن است بیرون DB همچنان اثر بگذارد. پیشنهاد اجرا: گذرگاه اثر خارجی باید lease/epoch و SHA موردانتظار مقصد را درست در زمان اثر بررسی کند، هویت/اختیار run قدیمی لغو شود و اثر مقصد idempotent باشد. این‌ها طراحی‌اند، نه ویژگی این نسخه. exactly-once خارجی ادعا نمی‌شود.

سیاست retention/آرشیو و tombstone، سهمیهٔ درخواست/هم‌زمانی و میزبان، امضای cursor، export رکورد قدیمی بزرگ و کنترل ساعت/لغو هویت هنوز بازند. هیچ حذف تاریخچه‌ای برای حل رشد DB انجام نشده است. راه‌حل چندمیزبانه در دامنه نیست. پیش از هر اتصال واقعی، طراحی هویت و مجوز، مدل تهدید، اجرای ایزوله و بازبینی مستقل لازم است.
