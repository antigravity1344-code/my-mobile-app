## F-02: هویت مستقل و ورودی مورد اعتماد

یک ingress مستقل باید هویت را از نشست یا هویت workload تأییدشده بگیرد و context احراز‌شده را جدا از payload به مدیر بدهد؛ فیلدهای خوداظهاری نباید این context را بازنویسی کنند. اعتبارسنجی صادرکننده، مخاطب، انقضا، لغو و اتصال هویت به اجرای مشخص لازم است. اسرار فقط در مخزن اختصاصی اسرار با حداقل دسترسی نگهداری شوند؛ هرگز در گزارش، SQLite، فرمان یا لاگ ثبت نشوند. صدور یا تعویض اعتبارنامه خارج از این مأموریت است.

ingress باید مخزن و شمارهٔ PR، شناسه و نویسندهٔ دستور را از GitHub معتبر دوباره بخواند؛ مجاز بودن نویسنده را با سیاست مالک بررسی کند. تأیید مالک باید رکوردی مستقل و قابل ممیزی باشد که به شناسهٔ مأموریت، hash محتوای دستور، base SHA، شاخه، اعمال مجاز و زمان انقضا متصل است. `ownerApproved: true` کافی نیست. ویرایش دستور یا تغییر دامنه، تأیید پیشین را نامعتبر کند. حساب GitHub مشترک به‌تنهایی هویت عامل‌های مختلف را ثابت نمی‌کند؛ انتساب جداگانه لازم است.

| نقش پیشنهادی | دامنهٔ اختیار |
| --- | --- |
| مالک/ناظر | تأیید ثبت، تصمیم REVIEW و retry با revision؛ محدود به مخزن و مأموریت |
| عامل اجرا | claim/start/heartbeat/finish فقط برای نقش، مأموریت و run متصل به هویت خودش |
| گزارشگر | خواندن outbox مجاز و ثبت رسید تحویل؛ بدون اجرای کار یا تصمیم ناظر |
| خواننده | خواندن مجاز و صفحه‌بندی‌شده؛ بدون تغییر |

deny-by-default و جداسازی عامل اجرا از تصویب‌کننده لازم است. اختیار واقعی نوشتن شاخه باید توسط runner/GitHub اعمال شود، نه صرفاً فهرست actions در DB. ادغام، deploy، حذف و force push بدون مسیر مجوز مستقل ممنوع بمانند.

پیشگیری از تکرار باید دو لایه داشته باشد: شناسهٔ تحویل ingress با قید یکتا، و کلید idempotency فرمان مقید به principal، مخزن، مأموریت و hash payload. payload متفاوت با همان کلید رد شود؛ retry همان فرمان پاسخ تاریخی بگیرد، نه lease تازه. تأیید منبع، ثبت فرمان و outbox باید قرارداد بازیابی تراکنشی روشنی داشته باشند. لغو مجوز و replay قدیمی نیز باید در سیاست دسترسی خواندن پاسخ لحاظ شوند.

## F-03: حدود ورودی پیش از parse/hash و خروجی محدود

پیشنهاد اولیه برای بررسی بعدی: سقف 262144 بایت UTF-8 برای کل فرمان، عمق JSON حداکثر 32، حداکثر 10000 عضو/عنصر، timeout خواندن و سقف درخواست هم‌زمان. این اعداد هنوز اجرا یا برای بار واقعی تأیید نشده‌اند. ورودی باید به‌صورت جریانِ محدود خوانده شود؛ محدودیت بایت روی محتوای decompressed نیز اعمال شود. UTF-8 نامعتبر رد شود. یک tokenizer محدود که رشته و escape را درست تشخیص می‌دهد باید پیش از `JSON.parse` و hash عمق را بشمارد، یا parser جریان‌دار با همین حدود استفاده شود. شمارش آکولاد خام درست نیست. بعد از آن schema، تعداد فیلدها و طول رشته‌ها بررسی و فقط سپس canonicalization/hash انجام شود. مسیر CLI، API، فایل تنظیمات و replay باید سیاست ورودی مشخص داشته باشند؛ خطا بدون درج فرمان یا نشت payload برگردد.

برای events و outbox پیشنهاد: cursor مبتنی بر seq/id با snapshot سقف توالی، پیش‌فرض 100 و حداکثر 500 ردیف، و سقف 1 MiB برای پاسخ. ترتیب ثابت و ادامهٔ صفحه بدون حذف/تکرار رکورد لازم است؛ رکورد منفرد بزرگ باید مسیر خطای مشخص یا دریافت جزئی داشته باشد. تعداد فراخوانی و حجم خواندن نیز محدود شود.

نگهداری تاریخچه نیازمند تصمیم مالک دربارهٔ مدت و الزام ممیزی است. انتقال به آرشیو باید قابل بازیابی و قابل راستی‌آزمایی باشد؛ رکورد فعال، outbox تحویل‌نشده، و وابستگی‌های زنده حذف نشوند. tombstone شناسهٔ مأموریت/فرمان و hash برای جلوگیری از اجرای مجدد قدیمی حفظ شود؛ پاک‌سازی سادهٔ جدول commands بازپخش را دوباره قابل اجرا می‌کند. تغییر triggerهای append-only یا حذف تاریخچه در این مأموریت مجاز نیست. برنامهٔ ظرفیت، پشتیبان و آزمون بازیابی پیش‌نیاز هر سیاست retention است.

## اتصال احتمالی GitHub و مجری زنده

این بخش طراحی است، نه مجوز راه‌اندازی. گزارشگر آینده باید outbox را با marker ثابت تحویل دهد، پس از timeout وجود همان marker را reconcile کند، سپس رسید واقعی را ثبت کند. crash بین ارسال و رسید ممکن است گزارش تکراری بسازد؛ تضمین exactly-once خارجی بدون پشتیبانی مقصد ادعا نشود. webhook باید امضا، timestamp و delivery ID معتبر داشته باشد؛ payload آن صرفاً اعلان است و دستور معتبر دوباره خوانده می‌شود.

runner آینده نیازمند محیط ایزوله، allowlist ابزار و مخزن/شاخه، محدودیت زمان/منابع/شبکه و کنترل لغو است. epoch داخلی به‌تنهایی نوشتن خارجی عامل منقضی را متوقف نمی‌کند؛ نوشتن باید از gateway بررسی‌کنندهٔ fencing و expected SHA عبور کند یا اختیار عامل قدیمی پیش از اجرای جدید لغو شود. مجری Codex و UX/UI فعلی همچنان شبیه‌ساز باقی می‌مانند.

پیش‌نیاز اجرا: تصویب طراحی توسط مالک، مدل تهدید، انتخاب هویت قابل اعتماد، تست جعل principal/approval و دسترسی متقاطع، replay و ویرایش دستور، fuzz ورودی عمیق/بزرگ و UTF-8 نامعتبر، آزمون رقابت/قطع شبکه و بازیابی گزارش، و بازبینی مستقل دسترسی‌ها. ریسک‌های باقیمانده شامل تصاحب نشست، حساب مشترک، رشد DB، نشت گزارش و اثر خارجی عامل منقضی است. هیچ اتصال زنده یا آمادگی production با F-01 اثبات نمی‌شود.
